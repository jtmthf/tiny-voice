## Why this matters

The lockfile resolves `@tanstack/start-server-core@1.167.29`, which is
vulnerable to GHSA-9m65-766c-r333 ("inbound server-function request
deserialization could invoke a sibling client-referenced server function"),
patched in `1.167.30`. Server-function dispatch is the mechanism **every**
mutation in `src/app/fns/` rides on, so this is the one runtime-relevant
advisory in the audit. Alongside it: three high-severity transitive `undici`
advisories (build-time only, via cheerio in `start-plugin-core`), an unused
`server-only` package that implies a server-boundary mechanism the repo doesn't
use, and `nitro` hard-pinned to a dated beta. For a demo repo whose thesis is
"the tooling keeps you honest," a dirty `pnpm audit` and a misleading manifest
undercut the point.

## Steps

### Step 1: Refresh the TanStack Start resolution

Run `pnpm update @tanstack/react-start`. This should re-resolve
`@tanstack/start-server-core` to `>=1.167.30` within existing caret ranges.

**Verify**: `pnpm ls @tanstack/start-server-core` → every printed version is
`>= 1.167.30`, and `pnpm audit --prod` no longer lists the
`start-server-core` advisory.

### Step 2: Override transitive undici

Add to `package.json`:

```json
"pnpm": {
  "overrides": {
    "undici": ">=7.28.0"
  }
}
```

Run `pnpm install`.

**Verify**: `pnpm audit --prod` → zero high-severity `undici` advisories.
Then `pnpm build` → exit 0 (the override touches build tooling; the build is
the test).

### Step 3: Remove the unused `server-only` package

Delete the `"server-only"` line from `dependencies`, run `pnpm install`.

**Verify**: `grep -rn "server-only" src package.json` → no matches;
`pnpm typecheck && pnpm build` → exit 0.

### Step 4: Evaluate the nitro beta pin (bounded attempt)

1. `pnpm view nitro versions --json | tail -40` — look for a `3.0.x-beta`
   newer than `3.0.260429-beta`.
2. If none exists: record "no newer beta as of <date>" in your report and skip
   to Step 5.
3. If one exists: bump the pin to the newest 3.0 beta, `pnpm install`, then
   `pnpm build` and `pnpm test:e2e:critical`.
4. If the build or e2e fails: **revert the nitro bump entirely**
   (restore the previous pin, `pnpm install`), note the failing version and
   error in your report, and continue. Do not debug nitro internals.

**Verify**: either the bump is in place with `pnpm build` + e2e green, or the
pin is unchanged and the failure is documented.

### Step 5: Full gate

**Verify**: `pnpm typecheck && pnpm lint && pnpm deps && pnpm test && pnpm build`
→ all exit 0. Run `pnpm test:e2e:critical` if not already run in Step 4.
